# Generating HLP/SPD natively (hlp_data.esf / spd_data.esf)

Status: **proposal**, written 2026-09-29 during the 190E map rebuild. Nothing here is implemented yet. Facts are
marked as **observed**; everything else is a hypothesis to be tested.

## Why

Every map change needs new `campaign_maps/<map>/hlp_data.esf` and `spd_data.esf`. Without them (or with stale ones
from another map) the startpos build dies creating the campaign AI (`std::bad_alloc` in CAI_INTERFACE, seen on
both Guandu and 190E). Today the only generator is the game itself, driven by RPFM's `build_starpos` with
`process_hlp_spd = true`, and it is slow:

- **Observed:** exactly **1.00 core** of 16 for the whole run (10.0 CPU-s per 10 wall-s, 74 threads).
- **Observed:** 20+ minutes on the reworked 190E map (1132×840 hexes, ~105k more passable hexes than 190E).
- It is launched through the game, so it can't be parallelised, split or resumed, and it prints nothing while it
  runs. Its intermediate results can't be inspected either.

A native generator (Atlas3K, C#) could build these files in parallel in seconds, and would slot in as another
`build-campaign` step next to rasters / global_map / camera_heightmap (see `native_campaign_build.md`).

## What the files are (observed)

Both are ESF, magic `0xABCA` (the compact encoding), each holding **one** root record:

| File | Root node | Vanilla dlc07 (892×702) | 190E (892×702, more regions) |
|---|---|---|---|
| `hlp_data.esf` | `CAI_TRANSITION_DATA` | 116,483 bytes | 140,745 bytes |
| `spd_data.esf` | `CAI_SIMPLE_PATH_DIRECTORY` | 25,201,233 bytes | 35,390,938 bytes |

- Header: `CA AB 00 00`, `00 00 00 00`, a timestamp, then the offset of the node-name table (one name each).
- **HLP** payload: short runs of compact values, mostly `07 xx xx` (u16) with `13`/`14`/`15`/`16`/`17`
  small-int codes. That reads like a list of transitions (id pairs plus costs) between a modest number of nodes.
- **SPD** payload: a few header ints, then long runs of `16 10` (a 16-element block) of `08 FF FF FF FF` (u32
  `0xFFFFFFFF`). It reads like a large lookup matrix, mostly "no entry", indexed by some node pair.
- **Interpretation (hypothesis):** "HLP" = the campaign AI's *high-level pathfinding* graph (the transitions
  between coarse areas), and "SPD" = a *simple path directory*: precomputed routes or next-hops between those
  areas for fast AI queries. SPD is 25–35 MB and grows faster than the map, which fits an all-pairs table.
- **Observed:** the generator is in `Three_Kingdoms.exe`. It's the only binary containing `CAI_TRANSITION_DATA` /
  `CAI_SIMPLE_PATH_DIRECTORY`, next to the strings `hlp_data`, `spd_data` and
  `empirecampaignaihlpdebugview` ("Is the campaign ai hlp debug view enabled"), which is a debug view to find
  the code with.

## Likely inputs (hypothesis)

What the generator can read at that point in startpos creation:

- `map_data.esf` and `pathfinding.ppd` (CAIME). CAIME's pathfinding export already builds **tile groups**,
  **HLCI** ("high-level connectivity info"), roads and bridges. HLP's nodes are probably those tile groups or
  something close.
- The settlements, ports and regions from the startpos tables (the AI paths between places it cares about).
- Movement costs by terrain type and road from the DB (`campaign_map_*` / ground types).

If SPD is all-pairs shortest paths over the HLP graph, the expensive part is one Dijkstra per source node. That
is embarrassingly parallel: 16 cores would give about 16× on its own, before any algorithmic gain over the game's code.

## Plan

**Phase 1 — ESF (ABCA) reader/writer in `Atlas3K.Formats`.**
Round-trip byte-exact on all four files we have (vanilla + 190E HLP/SPD) and on `map_data.esf`. Needed anyway;
the repo has no ESF code yet.

**Phase 2 — decode the two schemas (black box).**
- We have three reference pairs from different maps: vanilla, 190E and Guandu (`GuanDu.pack`, generated by the
  game on a 1328×784 map). Soon a fourth: reworked 190E.
- Dump both trees to JSON. Line up counts against CAIME outputs: number of tile groups / HLCI entries in
  `pathfinding.ppd`, number of regions, settlements and ports.
- Change one thing and diff (the method that cracked the BOB formats): a small test map from CAIME, one bridge
  removed, one road added. Regenerate through the game (slow but scriptable) and see which HLP/SPD entries move.
- Deliverable: a field-by-field spec, as in `docs/bob_campaign_build.md`.

**Phase 3 — find the generator in the exe (white box, if phase 2 stalls).**
- Start from the string xrefs above with `research/bob_re/disasm_grep.py` / `disasm_calls.py` and Ghidra
  (we have `ghidra_*.log` sessions from the BOB work).
- Look for the loops that fill `CAI_TRANSITION_DATA` and `CAI_SIMPLE_PATH_DIRECTORY` before serialisation, the
  cost function, and the tie-breaking order.
- Hardware breakpoints only (`ba e1`); a software `bp` trips the exe's integrity check (Guandu §10).

**Phase 4 — generator.**
- C# step `hlp_spd` in `CampaignBuildPipeline.AllSteps`: build the HLP graph from map_data/pathfinding.ppd plus
  the DB, then SPD with `Parallel.For` over source nodes.
- Output to the pack layout (`campaign_maps/<map>/hlp_data.esf`, `spd_data.esf`).

**Phase 5 — parity and a game test.**
- Byte-compare against the vanilla, 190E and Guandu references (a `CampaignBuildTests` case each).
- If byte parity fails only on ties or ordering, try functional parity: build a startpos with our files and let
  the AI run a few turns. BOB's river numbering showed that internally consistent but differently-numbered
  output can still be accepted.

## Effort and risks

- **Effort:** phase 1 is small (about a day). Phases 2–3 are the real unknown: comparable to the BOB
  global_props / tile_list work, days rather than hours. Phase 4 is small once the spec exists.
- **Risk — hidden inputs:** costs may come from DB tables we don't track yet. Phase 2's diff tests should
  surface them.
- **Risk — ordering:** if the game validates SPD against its own recomputation, or relies on a specific
  tie-break, we need the exact algorithm (phase 3) rather than just an equivalent one.
- **Risk — ESF variants:** ABCA compact types vary between games. Our four files are the test set; anything
  outside them has to be reported, not guessed.

## Meanwhile

- Build HLP/SPD only when the map itself changes. DB-only edits (owners, names, characters) still need a
  startpos rebuild, but not new HLP/SPD.
- Give the game process High priority during `build_starpos` (done for the 190E build), keep the power plan
  on high performance, and don't run other heavy jobs alongside it. That's a small gain, not a multiple.
- Never let a lower-priority pack supply stale HLP/SPD for a changed map. The map pack must ship its own. For
  190E, `!!190_expanded_region_test.pack` still carries the old map's files, and that is our lead suspect for
  the first `bad_alloc` crash on 2026-09-29.
